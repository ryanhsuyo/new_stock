# L2.0 Multi-Touch Trendline Design

Status: implemented

Date: 2026-06-22

## Goal

Improve trendline quality by validating candidate lines against multiple swing
points while preserving the existing two-endpoint API and frontend chart.

## Existing Contract

`TrendLine` remains unchanged:

```python
class TrendLine(BaseModel):
    valid: bool
    p1: PricePoint | None
    p2: PricePoint | None
    note: str
```

The frontend continues drawing and extending the line through `p1` and `p2`.
No API field, TypeScript type, router, or chart code changes.

## Selected Behavior

For both ascending support and descending resistance trendlines:

1. Generate every chronological pair of detected swing points that has the
   required direction.
2. Use the pair's row indexes to define a straight line.
3. Project that line onto every swing from the first endpoint through the most
   recent swing.
4. Count a swing as a touch when its price is within 2% of the projected line.
5. Reject the candidate if a later swing violates the line by more than 2% in
   the risk direction.
6. A candidate needs at least three touches, including its two endpoints, to be
   considered multi-touch confirmed.
7. Select the best valid candidate by touch count, then most recent second
   endpoint, then widest row span.
8. If no candidate has three touches, use the existing latest valid two-point
   rule unchanged.

## Direction Rules

### Ascending Support

Candidate endpoints must satisfy `p2.price > p1.price`.

For a projected price `line_price`:

* Touch: `abs(low - line_price) / line_price <= 0.02`.
* Invalid: a swing low is below `line_price * 0.98`.
* A swing low well above the line is allowed but is not a touch.

### Descending Resistance

Candidate endpoints must satisfy `p2.price < p1.price`.

For a projected price `line_price`:

* Touch: `abs(high - line_price) / line_price <= 0.02`.
* Invalid: a swing high is above `line_price * 1.02`.
* A swing high well below the line is allowed but is not a touch.

All market prices and projected prices must be positive. Non-positive candidate
data is rejected rather than divided.

## Candidate Ranking

Rank only non-violated candidates with at least three touches by:

```python
(touch_count, p2_row_index, p2_row_index - p1_row_index)
```

Higher values win. This favors stronger confirmation first, then relevance,
then useful span. Stable iteration order breaks an exact tie.

The returned `p1/p2` are still the endpoints that define the chosen slope. A
third or later validating touch is described in `note`, not added to the model.

## Notes

Multi-touch ascending line:

```text
連接遞增擺盪低點，多點確認（3 個有效觸點）
```

Multi-touch descending line:

```text
連接遞減擺盪高點，多點確認（4 個有效觸點）
```

Fallback notes remain the existing two-point wording. `valid=false` messages
also remain unchanged.

## Architecture

Keep orchestration in `analysis_service.py` and add small private helpers:

```python
def _row_indexes_by_date(rows: list[dict]) -> dict[str, int]: ...

def _select_multi_touch_pair(
    rows: list[dict],
    swings: list[dict],
    *,
    direction: str,
    tolerance: float = 0.02,
) -> tuple[dict, dict, int] | None: ...
```

`_build_uptrend_line` and `_build_downtrend_line` try the helper first, then
execute their current nested-loop fallback. Swing detection remains unchanged
and continues using only the latest 120 bars.

No trendline result is used to alter the batch signal score in this phase. This
work only improves the single-stock technical-analysis trendline.

## Error Handling

Return no multi-touch candidate when:

* Fewer than three swings exist.
* A swing date cannot be mapped to the supplied rows.
* Endpoint indexes are not chronological.
* A projected price is non-positive.
* Every candidate has a risk-direction violation.

The builder then uses the existing two-point fallback. Invalid input therefore
does not create an API error or silently remove a previously available line.

## Tests

Tests use fixed rows and monkeypatched swing lists where exact geometry matters.

Required cases:

* Three ascending lows on one line produce a multi-touch uptrend line.
* Three descending highs on one line produce a multi-touch downtrend line.
* A later low more than 2% below ascending support rejects that candidate.
* A later high more than 2% above descending resistance rejects that candidate.
* Candidate ranking prefers more touches over a merely newer two-point pair.
* With only two directional swings, existing fallback output remains valid and
  keeps the old note.
* Invalid dates or non-positive projections safely fall back.
* Existing stock-analysis API schema and complete backend tests remain green.

## Rule Documentation

Update `current_rules.md` and `signal_rules.md` before implementation:

* Multi-touch validation uses 2% tolerance.
* Risk-direction violations invalidate a multi-touch candidate.
* At least three touches are required for the multi-touch label.
* The API still exposes two defining endpoints.
* Two-point fallback remains for backward compatibility.

## Scope

In scope:

* Multi-touch candidate validation and selection.
* Existing trendline builder notes.
* Fixed unit and stock-analysis regression tests.
* Rule, phase, status, and execution documentation.

Out of scope:

* Adding `anchors[]` or changing `TrendLine` schema.
* Frontend/chart changes.
* Linear regression or sloped support zones.
* Changing batch signals, scores, trades, holdings, or cash.
* Reading or rewriting real OHLCV/generated output files.

## Acceptance Criteria

* Three or more valid touches produce an explainable multi-touch line.
* A material support/resistance violation disqualifies the candidate.
* Two-point behavior remains available when multi-touch evidence is absent.
* API and frontend contracts remain unchanged.
* Focused and complete backend tests pass using fixed data only.
