# R2.0 Data Calendar, Coverage, And Lineage Design

Status: implemented

Date: 2026-06-23

## Goal

Make daily outputs more trustworthy by explaining whether the latest data date is
a real expected trading day, which tracked symbols are missing or stale, and
which local update batch produced the current signal files.

## Problem

R1 proved a single-stock backtest can avoid future data and account for costs.
The next trust gap is input reliability:

* stale checks currently use weekday logic, not an explicit local market
  calendar.
* coverage exists in scattered summaries but not as a first-class generated
  report.
* `summary.json`, `universe_report.csv`, `daily_brief.json`, and
  `update_status.json` do not share a single run lineage contract.

Without this, a result can be technically correct but still hard to audit.

## Considered Approaches

Recommended: local calendar plus generated coverage and batch metadata.

* Add a small service for trading-day decisions.
* Store optional local holiday overrides in `backend/data/trading_calendar.json`.
* Generate `backend/out/data_coverage_report.json` from existing OHLCV and
  leaders.
* Stamp update outputs with a deterministic batch ID and input snapshot fields.

This gives immediate value without network dependencies or new frameworks.

Alternative: fetch an official TWSE holiday calendar during every update. This
could be more complete, but it makes tests brittle and adds an external source
before the local contract is stable.

Alternative: only enhance `doctor.py`. This is smallest, but it keeps coverage
as a diagnostic side path instead of making it part of the product workflow.

## Scope

In scope:

* Taiwan stock trading-day helper with weekend handling and optional local
  holiday overrides.
* Coverage report for `leaders.json` versus `ohlcv.csv`.
* Reasons for missing, insufficient, lagging, or OK symbols.
* A generated batch ID attached to update status and signal outputs.
* Workflow and doctor checks that point to the coverage report.
* Network-free tests using temporary backend data.

Out of scope:

* Downloading official holiday calendars.
* Frontend changes.
* Database, scheduler rewrite, or new dependencies.
* Modifying trades, holdings, cash, decision journal, or existing generated
  output files by hand.
* Perfect historical exchange-calendar completeness.

## Data Contracts

`backend/data/trading_calendar.json` is optional. When absent, the system uses
weekends only.

```json
{
  "market": "TW",
  "holidays": ["2026-06-19"],
  "makeup_trading_days": ["2026-02-07"]
}
```

`backend/out/data_coverage_report.json` is generated by services/scripts:

```json
{
  "generated_at": "2026-06-23T20:00:00",
  "batch_id": "20260623T120000Z-a1b2c3d4",
  "expected_trading_day": "2026-06-22",
  "raw_ohlcv_as_of": "2026-06-22",
  "tracked_count": 100,
  "ok_count": 95,
  "coverage_pct": 95.0,
  "symbols": [
    {
      "code": "2330",
      "row_count": 240,
      "last_data_as_of": "2026-06-22",
      "status": "ok",
      "reason": "資料已覆蓋最新預期交易日"
    }
  ]
}
```

Batch metadata is lightweight and local:

* `batch_id`
* `run_started_at`
* `run_finished_at`
* `input_ohlcv_mtime`
* `input_ohlcv_size`
* `raw_ohlcv_as_of`
* `coverage_report_path`

## Architecture

Create `backend/app/services/trading_calendar_service.py` for pure calendar
logic. Reuse it from `app.utils.count_missed_trading_days()` so old callers keep
their public API while gaining holiday overrides.

Create `backend/app/services/data_coverage_service.py` for reading leaders and
OHLCV, computing symbol statuses, writing generated coverage JSON, and returning
summary metrics.

Update existing services instead of adding routers:

* `update_service.run_full_update()` creates a batch ID and writes it into
  `update_status.json`.
* `signals_service.run_daily_signals()` accepts optional lineage metadata and
  includes it in `summary.json`.
* `daily_update.py` / `update_all_data.py` keep thin orchestration.
* `doctor.py`, Daily Check, and Update Workflow read the coverage report and
  expose blockers or warnings.

## Acceptance Criteria

* A configured holiday does not make data stale on the next calendar day.
* A configured makeup trading day is counted as a missed trading day.
* Coverage report lists every tracked symbol with status and reason.
* Update Workflow blocks when coverage is below the chosen threshold or outputs
  lag raw OHLCV.
* `update_status.json` and `summary.json` share the same batch ID after a full
  update.
* Tests use fixed local files and no real network.
* No frontend, real trading data, or manually edited `backend/out/*` changes.

## Risks

The first version is only as complete as the local holiday override file. This
is acceptable because it removes false confidence, keeps behavior explainable,
and leaves a clear future path for official calendar import.
