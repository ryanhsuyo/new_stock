# F52 Heartbeat Safe Backlog Plan

Status: planning

Purpose:

Give scheduled heartbeat development a concrete queue of safe, product-like slices after F51, so it does not repeatedly conclude that there is nothing to do while the system is healthy but still has user-facing blockers.

## Current Baseline

As of 2026-07-04:

* Active phase: none.
* Latest completed phases: F50 / F51, covering structured `signal_alerts.preview_alerts` and PM Worklist rendering.
* Data outputs are fresh for `2026-07-03`; `today_scan.data_freshness.stale_count = 0` and `missing_date_count = 0`.
* `daily_check.can_use_trade_outputs = false` because `signal_alerts` remains a block-level manual review item.
* Additional warnings remain: stale manual market note and incomplete fundamentals coverage.

## Operating Rule

When no active phase exists, heartbeat should pick the first safe phase below that is still applicable.

Do not pick tasks that require:

* User investment judgment.
* Fake or inferred fundamentals.
* Changes to trades, holdings, cash, or formal personal records.
* A new data provider, database, queue, or large framework.
* Frontend recomputation of strategy, score, blocker, PM priority, or fundamentals logic.

## Recommended Phase Queue

### F52 — Signal Alerts Review Usability

Goal:

Make the existing signal-alert blocker easier to review without auto-clearing it.

Safe slices:

* Add a backend-owned review checklist summary for block alerts, e.g. counts by `review_focus`.
* Add PM Worklist / Daily Check wording that says exactly what the user should compare for the first 5 block alerts.
* Add a "copy review checklist" payload generated by backend, not frontend.

Stop conditions:

* Do not add an acknowledgement / resolve mechanism yet.
* Do not mark alerts reviewed or unblock trade outputs automatically.

Suggested verification:

* `backend/tests/test_daily_check.py`
* `backend/tests/test_pm_worklist.py`
* frontend structure test if UI rendering changes.

### F53 — Manual Market Note Action Clarity

Goal:

The stale manual market note warning should be clear enough that the user knows what to write next.

Safe slices:

* Add backend-provided `example_payload` / checklist for `POST /api/stocks/market-notes`.
* Show current stale note date, signal as-of date, and required fields in one compact PM action.
* Keep it as guidance only; no automatic note creation.

Stop conditions:

* Do not invent market opinion.
* Do not save a note without user input.

Suggested verification:

* `backend/tests/test_daily_check.py`
* `backend/tests/test_pm_worklist.py`
* frontend structure tests if Dashboard changes.

### F54 — Fundamentals Warning Truthfulness

Goal:

Make Quality Momentum Lite fundamentals coverage honest when data is missing.

Safe slices:

* Ensure zero or low fundamentals coverage is worded as "未完成 / 無法評分", not as a real neutral score.
* Surface PE-only apply status separately from blocked derived fields.
* Add tests that `fundamental_data_ok=false` cannot look like a complete score.

Stop conditions:

* Do not fabricate ROE, FCF, interest coverage, dividend years, 5-year averages, or CAGR.
* Do not loosen Quality Momentum Lite rules unless a separate design phase approves it.

Suggested verification:

* `backend/tests/test_signals_*.py`
* `backend/tests/test_daily_check.py`
* `backend/tests/test_official_fundamentals_*.py` when touched.

### F55 — Signal Alerts Acknowledgement Decision Spec

Goal:

Plan, but do not yet implement, a safe way for the user to mark signal alerts as reviewed.

Safe slices:

* Write a decision/spec doc comparing: no acknowledgement, decision-journal based acknowledgement, or separate review file.
* Define what is allowed to unblock `can_use_trade_outputs`.
* Identify audit trail requirements.

Stop conditions:

* Do not implement write behavior without explicit user approval.
* Do not modify trading records.

Suggested verification:

* Docs sanity only.

### F56 — Today Scan Empty-State Explainability

Goal:

When Today Scan has no candidates or is blocked by Daily Check, the UI should explain whether the reason is "no setup" or "outputs blocked".

Safe slices:

* Add backend-owned empty-state reason fields if missing.
* Show blocked-by-Daily-Check wording in Dashboard without recomputing candidates.
* Keep daily vs weekly wording consistent.

Stop conditions:

* Do not create candidates in frontend.
* Do not reinterpret strategies.

Suggested verification:

* `backend/tests/test_today_scan_*.py`
* frontend Today Scan structure tests.

### F57 — Update / Scheduler Health Readiness

Goal:

Make it obvious whether daily update is automated, stale, failed, or manual-only.

Safe slices:

* Read existing update status and operations docs.
* Add a product-visible health message if scheduling is not installed or update logs are old.
* Add a copyable "manual daily update" fallback command.

Stop conditions:

* Do not install launchd or edit files outside the repo unless user explicitly asks.
* Do not run long network updates unless user asks or an active phase explicitly requires it.

Suggested verification:

* `backend/tests/test_update_status.py`
* Update Workflow tests.

### F58 — Two-Strategy Contract Regression

Goal:

Keep old_wang and steady_momentum as the only product strategy buckets.

Safe slices:

* Add or tighten tests scanning API / output contracts for visible strategy buckets.
* Ensure docs mention `core_technical_v2` as internal only.
* Verify frontend selectors and labels remain two-strategy only.

Stop conditions:

* Do not add a third strategy.
* Do not rename existing strategy IDs without migration.

Suggested verification:

* backend strategy/catalog tests.
* `node --test frontend/tests/two-strategy-ui.test.mjs`

## Priority Recommendation

Next safe implementation phase should be:

1. F52 Signal Alerts Review Usability, because it addresses the current hard blocker without changing trading state.
2. F53 Manual Market Note Action Clarity, because it addresses the next warning without inventing market commentary.
3. F54 Fundamentals Warning Truthfulness, because it protects user trust in Quality Momentum Lite.

If the user wants heartbeats to keep actively developing, start with F52 and keep each slice small enough to complete, verify, and commit in one heartbeat turn.
