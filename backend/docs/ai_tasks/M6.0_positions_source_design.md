# M6.0 Position Source Authority Design

Status: implemented

Date: 2026-06-21

## Goal

Make `trades.json` the authoritative source for signal holdings whenever it can
be loaded successfully. An empty trade-derived portfolio must remain empty and
must not resurrect stale holdings from `positions.json`.

## Problem

`signals_service._load_positions()` currently falls back to `positions.json`
whenever the holdings calculated from trades are empty. This confuses two
different states:

* `trades.json` loaded successfully and legitimately produced no holdings.
* `trades.json` could not be loaded or parsed.

The first state can occur after all positions are sold or after trades are
explicitly cleared. Falling back in that state may reintroduce stale legacy
holdings into signal classification and holding-weight annotations.

## Selected Behavior

1. Load and calculate holdings from `trades.json`.
2. If loading and calculation succeed, return `source="trades"` even when
   `holdings` is empty.
3. Use `positions.json` only when trade loading or calculation raises an
   exception.
4. If fallback is needed but `positions.json` is missing, return an empty
   non-tradable position snapshot with `source="none"`.
5. Log the trade-source failure before using fallback; do not silently swallow
   the exception.

## Data Contract

The return shape remains compatible:

```python
{
    "cash": 0,
    "holdings": {},
    "source": "trades",
}
```

Possible `source` values remain:

* `trades`: trade loading and position calculation succeeded.
* `positions`: trade loading or calculation failed and the legacy file loaded.
* `none`: trade loading or calculation failed and no legacy fallback exists.

No API schema, router, frontend, trade record, or generated output format is
changed.

## Scope

In scope:

* Refine `_load_positions()` control flow in `signals_service.py`.
* Add fixed tests for empty trades, fully sold positions, valid trade holdings,
  fallback on trade failure, and missing fallback.
* Reconcile M6 status and the operational/rule documentation.

Out of scope:

* Deleting `positions.json`.
* Migrating or rewriting user data.
* Changing trade import, buy, sell, clear, restore, or portfolio APIs.
* Adding a database or new dependency.
* Frontend changes.

## Error Handling

The fallback path is entered only from an explicit exception boundary around
trade loading and position calculation. A fallback JSON parse error must remain
visible rather than being presented as a valid empty portfolio.

The warning must identify the failed primary source and that the legacy
fallback is being attempted. It must not include private trade contents.

## Tests

Tests use monkeypatched fixed records and temporary paths; they do not read or
write real `backend/data/trades.json` or `backend/data/positions.json`.

Required cases:

* Empty trades return `source="trades"` and empty holdings even when a legacy
  positions file contains holdings.
* Buy then full sell returns `source="trades"` and empty holdings.
* Open trade holdings preserve fee-aware average cost behavior.
* Trade loading failure uses a valid legacy positions file.
* Trade loading failure with no legacy file returns `source="none"`.
* Existing signal and API regression suites continue to pass.

## Acceptance Criteria

* A successfully loaded empty trade ledger cannot revive stale legacy holdings.
* Valid open holdings still come from trades with the existing cost basis.
* Legacy fallback works only after a primary-source exception.
* No real trading, holding, cash, or generated output file is modified.
* Relevant focused tests and the complete backend test suite pass.

## Risks

* Users who previously relied on `positions.json` while keeping a valid empty
  `trades.json` will now see no holdings. This is intentional and matches the
  documented authority rule.
* `load_trades()` currently creates an empty ledger when the file is missing;
  that successful empty result is authoritative and will not use legacy data.
