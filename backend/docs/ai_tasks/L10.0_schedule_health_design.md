# L10.0 Schedule Health Design

Status: implemented

Date: 2026-06-21

## Goal

Expose whether the configured daily update schedule has actually run recently,
independently from whether market data currently appears fresh.

## Problem

`GET /api/system/data-status` reports data freshness and the most recent update
status, but it does not interpret `last_run_finished_at` as schedule health.
Manual backfill or signal generation can make outputs fresh while launchd or
cron has silently stopped running.

## API Contract

Add three fields to `DataStatus`:

```json
{
  "schedule_health_status": "healthy",
  "schedule_is_overdue": false,
  "schedule_health_message": "最近一次排程更新已完成，未錯過已結束的平日。"
}
```

`schedule_health_status` values:

* `healthy`: a valid completed run has not missed a completed weekday.
* `running`: `last_run_status` is currently `running`.
* `failed`: the latest run status is `failed`.
* `overdue`: the last completed run missed at least one completed weekday.
* `never_run`: no run status and no finished timestamp exist.
* `invalid_timestamp`: a terminal/unknown status lacks a valid ISO finished
  timestamp.

Only `overdue` sets `schedule_is_overdue=true`. Existing failed/running states
remain visible through both `last_run_status` and the new health status.

## Status Priority

Evaluate in this order:

1. `last_run_status == "running"` -> `running`.
2. `last_run_status == "failed"` -> `failed`.
3. No status and no `last_run_finished_at` -> `never_run`.
4. Missing or invalid finished timestamp -> `invalid_timestamp`.
5. Valid finished timestamp with one or more missed weekdays -> `overdue`.
6. Otherwise -> `healthy`.

This prevents a stale timestamp from changing a currently running or explicitly
failed job into `overdue`.

## Trading-Day Rule

Reuse `count_missed_trading_days`:

* The run's finished calendar date is the covered date.
* Today is excluded because today's scheduled close/update may not have occurred.
* Saturday and Sunday are excluded.
* If the last run finished Friday, Monday remains healthy; it becomes overdue on
  Tuesday if Monday's run never completed.
* Taiwan market holidays are not modeled, matching the existing data-stale rule.

Extend the utility with an optional `today` argument for deterministic tests;
existing callers continue using the real current date.

## Architecture

Add a pure helper in `update_service.py`:

```python
def _compute_schedule_health(
    last_run_status: str | None,
    last_run_finished_at: str | None,
    *,
    today: date | None = None,
) -> dict:
    ...
```

`get_data_status()` merges the returned fields into its existing response.
`DataStatus` declares the three fields with conservative defaults. The system
router remains thin and unchanged apart from its field documentation.

No status is persisted back to `update_status.json`; schedule health is derived
at read time so it cannot become stale itself.

## Error Handling

Accept standard ISO datetime strings supported by `datetime.fromisoformat`,
including timezone offsets. Invalid or missing terminal timestamps produce
`invalid_timestamp` with an actionable message rather than raising an API 500.

Messages must explain the state without exposing command output, credentials,
or file contents.

## Tests

Use fixed dates and dictionaries; do not read or write real output files.

Required cases:

* Never-run status.
* Running takes priority over an old/missing finished timestamp.
* Failed takes priority over an old/missing finished timestamp.
* Missing terminal timestamp is invalid.
* Malformed timestamp is invalid.
* Friday completion remains healthy on Monday.
* Friday completion is overdue on Tuesday.
* API schema includes all three fields.
* Existing data freshness fields remain unchanged.
* Complete backend test suite passes.

## Documentation

Update API and operations documentation to distinguish:

* `is_stale`: whether market data missed a completed trading weekday.
* `schedule_health_status`: whether the automated update process itself ran.

Mark L10 complete only after focused and full verification passes.

## Scope

In scope:

* Derived schedule health fields in `data-status`.
* Deterministic weekday-based tests.
* API, operations, status, and phase documentation.

Out of scope:

* Frontend changes or new alerts.
* Inspecting launchd or cron processes directly.
* Sending notifications.
* Taiwan holiday calendars.
* Changing update execution, locks, or persisted status format.
* Modifying trading records, generated signal outputs, or private data.

## Acceptance Criteria

* A silently missed weekday run becomes visible as `overdue`.
* Weekend transitions do not create false overdue warnings.
* Running, failed, never-run, and invalid timestamp states are deterministic and
  explainable.
* Data freshness semantics and existing API fields remain backward compatible.
* Tests use fixed inputs and never depend on the network or real output files.
